The client bundles the real SmartFoxServer 2X SDK but never actually uses its socket layer. Every byte on the wire is written by a hand-rolled reimplementation that only reuses SFS2X's data model, and the "encryption" bit is a length-derived XOR, not a cipher.

## Transport

Plain TCP socket, **no TLS**. Host/port/zone/connection-type arrive dynamically from the GSL response. Two connection types exist:

- `connectionType 0`: raw TCP, straight into the packet framing below.
- `connectionType 1`: a one-shot literal HTTP/1.1 `Upgrade: websocket` preamble is sent first, purely to satisfy load balancers that require a valid HTTP handshake, then the exact same raw SFS2X binary framing runs on the same socket. **This is not a real WebSocket**: there's no RFC 6455 frame masking anywhere in the read/write path. A Go client can dial TCP directly, or replay the literal handshake bytes if a load balancer demands them.

The 1.0.364 preamble is fixed (`NetHandShakeInterceptor` in `BaseUtils`; static-analysis-only):

- `Sec-WebSocket-Key: cmFuZG9t`, which is base64 for `random`, on every connection.
- `User-Agent: LastWarWebSocket`, plus fixed `Cache-Control`, `Pragma`, `Accept-Encoding`, `TE`, and `Content-Length` headers.
- The request path comes from the `ws://host/path` line URL and defaults to `/`.
- The client accepts the response on status 101, any 2xx, or 304. It never checks `Sec-WebSocket-Accept`.
- On these lines the first ping is a plain ping, not the `a=29` probe described below.

In 1.0.364, `client_config` switch 26 selects connection type 1 to the `ws_ip` host on port 80, and switch 44 makes every second connect retry use it (see [Server-controlled transport switches](#server-controlled-transport-switches)). `KCPMode` is always `"0"`, and the game socket never uses UDP; only the real-time PvP mini-games do, over a separate transport (see [Mini-game PvP transport](#mini-game-pvp-transport)). Sockets set `NoDelay`, a 2 MiB receive buffer, a 64 KiB send buffer, and 30 s send and receive timeouts (static-analysis-only).

## Gateway race and the pre-login probe

The GSL `serverList[].ip` field is a `|`-delimited list of gateway hosts for one zone, all on the same port. Two live GSL responses on 2026-10-04 listed the same three hostnames, with only the port differing by zone: `10783` for `APS783` and `10072` for a guest account on `APS72` (confirmed live):

```text
lastwar-game-tcp-aws-1.lastwargame.com|lastwar-game-tcp-gcp-1.lastwargame.com|lastwar-game-tcp-cf-1.lastwarapp.net
```

The Lua also carries two fallback "proxy lines", `ProxyList` in `Global/EnumType.lua`, named `aws` and `cf` by `ProxyName`. They use the zone's current `GameServerPort`, the C# reads them through `CSharpCallLuaInterface.GetAllProxy()`, and the in-game ping screen lists them. When C# switches to them wasn't traced (static-analysis-only):

```text
lastwar-game-us-aws-ali.lastwargame.com
lastwar-game-us-cf-ali.lastwarapp.com
```

A related helper, `CommonUtil.GetPortId(zoneId)`, returns `17000 + zoneId`.

A packet capture only shows the addresses these resolve to, so a session config written by `pcap -session-out` holds IP addresses; the hostnames work in its `ip` field too. The shipped client connects to all the gateways at once and keeps whichever answers first. This comes from the 1.0.364 C# (`ChooseLine`, `NetRawProxy`) and matches the 2026-10-04 capture of the real iOS app:

1. Open a TCP connection to every gateway in parallel.
2. On each, immediately send a `CustomPingPong` request (`c=0`, `a=29`).
3. The first gateway to answer with a pong wins. Close the others and save the winner as `SERVER_IP`.
4. Only then send `Login`.

The capture showed the race across three gateways, two IPv4 and one Cloudflare IPv6:

| | Winner (IPv4) | Cloudflare (IPv6) | IPv4 (the address an older session config pinned) |
|---|---|---|---|
| SYN-ACK | 19 ms | 14.5 ms | 77 ms |
| Probe sent | 25 ms | 26 ms | 88 ms |
| Pong | **154 ms** (first) | 162.5 ms | 162.5 ms |
| Afterwards | `Login` at 200 ms, 45 ms after the pong | FIN at 187 ms | FIN at 188 ms |

The three pongs carried `serverTime` values within 11 ms of each other, so all three front-ends reach one backend. The winner varies from run to run; an earlier capture had the pinned address winning.

The probe's `p` object is fixed: a masked, Android-login-shaped template with literal placeholder values, into which the client splices only the device's real `deviceId`, plus a `clientTime`. It's byte-identical across all three sockets apart from `clientTime`. Its purpose is unknown, and it may be an anti-fraud surface, so it's documented here as a protocol fact only. The reply is a plain pong, `{p:{serverTime, clientTime}}` with `serverTime` in ms. After the probe, every keepalive is a plain ping.

Per the C#, a gateway that times out at `Login` (7 s) is blacklisted and the connect is retried. A separate `NetLineSpeedTester` re-probes every gateway the same way for analytics, at most once per 25 s, and never switches lines (static-analysis-only).

`goclient` doesn't race. `DoCrossServerLogin` dials the `|` list in order, 10 s per host and IPv6-safe, sends no probe, and sends `Login` straight after connecting. The server accepts that order (confirmed live). The fallback is confirmed live too: with an unreachable TEST-NET address first in the list, the dial timed out after 10 s and the login went through on the next gateway. When `goclient` writes a changed address or token back to the session config, it keeps the list as long as the gateway it reached is on it.

## Packet envelope: three nested layers

```text
[1-byte header][2/4-byte length][ optional zlib compress → XOR "encrypt" ]
  body = SFSObject {
    "c": BYTE    controller id   (0 = System, 1 = Extension)
    "a": SHORT   action id       (1 = Login, 13 = CallExtension, 29 = PingPong)
    "p": SFS_OBJECT  content
  }
```

For every gameplay `cmd`, the `"p"` content is itself another SFSObject:

```text
SFSObject {
  "c": UTF_STRING   cmd        e.g. "mail.read"
  "r": INT          roomId     always -1 (SFS "Rooms" are unused entirely)
  "p": SFS_OBJECT   params     the command's own fields, plus an injected "_id" int
}
```

So a full `mail.read` request is schematically `{c:1, a:13, p:{c:"mail.read", r:-1, p:{uid:..., type:..., toUser:..., _id:42}}}`.

The real client puts `_id` on every extension request: `Login` carries `1`, and requests count up from `2`. The server echoes `_id` and adds `_time` (observed in the 2026-10-04 capture). `goclient` sets `_id` only on `Login` and `login.init`, and the server accepts that (confirmed live).

## Packet header bits

| Bit | Flag | Behavior |
|---|---|---|
| `0x80` | binary | always set |
| `0x40` | encrypted | always set on what the client sends, see XOR "encryption" below. Server-to-client frames in the 2026-10-04 capture (`0x80`, `0xB0`, `0xB8`) didn't set it and weren't XORed; `goclient`'s reader XORs only when the bit is set |
| `0x20` | compressed | set iff the uncompressed serialized payload > 1024 bytes (zlib deflate, level 9) |
| `0x10` | useLZ4 (repurposed) | never set on send; on receive the "LZ4" bit actually triggers **Zstandard** decompression, not LZ4, leftover naming from a migration. With `0x20` and `0x10` both set, a 4-byte big-endian uncompressed length follows the length field. **Implemented**: `ReadPacket` (`packet.go`) previously detected this branch correctly but just returned an error instead of decompressing, which read as connection-closed; now decodes via `github.com/klauspost/compress/zstd`, confirmed live against the server's ~313KB Zstd-compressed init bootstrap push |
| `0x08` | bigSized | set iff payload > 65535 bytes → 4-byte length instead of 2. The game's own sender is `NetPacket` in `BaseUtils` (`BaseUtils.decompiled.cs:33284-33324`); the embedded SmartFox2X 1.7.8 SDK's `SFSIOHandler` uses the same threshold (`SmartFox2X.decompiled.cs:31762-31783`). See [Which SDK is the reference](#which-sdk-is-the-reference). The 1.0.364 sender tests the uncompressed length; `goclient` tests the compressed length, which is harmless because it never sends packets that large |
| `0x04` | forward | a 2-byte big-endian server id follows the header byte, before the length. The 1.0.364 client sets it on **every** send when `client_config` switch 29 and the Lua switch `EnableServerRangeRouting` are both on. The id is the zone number: `BaseUtils`' `ParseSid("APS783")` returns 783 (static-analysis-only). The 2026-10-04 capture agrees: it shows the bit on every client-to-server frame (headers `0xE4` and `0xC4`), including the probe, with id `0x030F` = 783 for zone `APS783`. Likely gateway routing. `goclient` never sets it, and the server accepts that (confirmed live) |

### Send and receive framing differ

The 1.0.364 client writes and reads packets with two different classes (static-analysis-only):

- **Send** always uses the legacy `NetPacket`: header `0x80 | 0x40`, plus `0x20` with zlib when the uncompressed body is over 1024 bytes, plus `0x08` when it's over 65535, plus `0x04` and the server id when forwarding. The body is XORed against the little-endian bytes of its final length. The maximum is 1,000,000 bytes.
- **Receive** uses `NetPacketNew`: when `0x20` and `0x10` are both set, the 4-byte uncompressed length follows, and the body is Zstd-decompressed. When only `0x20` is set, it's zlib.

`goclient`'s `packet.go` already matches both sides.

<Warning>
**The "encryption" is not encryption**

```go
func Encrypt(data []byte) []byte {
    key := uint32LE(len(data))          // the on-wire length field, sent in cleartext
    for i := range data {
        data[i] ^= byte(key >> (8 * (i % 4)))
    }
    return data
}
```

The XOR keystream is derived entirely from the packet's own (cleartext) length field. No secret material, no negotiation, no per-session state. This is obfuscation, not confidentiality, and needs zero cryptographic material to implement in Go, just XOR the body against the little-endian length, computed after compression.
</Warning>

## `SFSObject` binary format

Big-endian throughout. A standalone serialized object is self-describing, it starts with its own tag byte and count.

| Tag | Type | Encoding |
|---|---|---|
| 0 | `NULL` | - |
| 1 | `BOOL` | 1 byte |
| 2 | `BYTE` | 1 byte |
| 3 | `SHORT` | 2 bytes, signed |
| 4 | `INT` | 4 bytes, signed |
| 5 | `LONG` | 8 bytes, signed |
| 6 | `FLOAT` | 4 bytes, IEEE-754 |
| 7 | `DOUBLE` | 8 bytes, IEEE-754 |
| 8 | `UTF_STRING` | u16 byte-length + UTF-8. The u16 allows 65535 B, but the client's encoder refuses strings over 32,767 B (SmartFox2X `ByteArray`), so a compatible sender should cap there too |
| 10 | `BYTE_ARRAY` | i32 count + N × element, the one array type that skips the shared size helper; the decompiled Unity SDK's `BinDecode_BYTE_ARRAY` calls a bare 4-byte `ReadInt` instead of `GetTypedArraySize`. A genuine SFS2X wire-format asymmetry, confirmed decoding the live 313KB init payload. |
| 9, 11–16 | `*_ARRAY` | i16 count + N × element (`GetTypedArraySize`) |
| 17 | `SFS_ARRAY` | i16 count, then N × (tag + payload), recursive |
| 18 | `SFS_OBJECT` | i16 key count, then N × (UTF_STRING key + tag + payload), recursive |
| 19 | `CLASS` | *not implemented*, never emitted |
| 20 | `TEXT` | i32 byte-length + UTF-8 (uncapped) |

*`BIG_NUM`, present in some SFS2X SDK builds, doesn't exist in this game's enum at all, no gap in the numbering. Not needed.*

## Which SDK is the reference

The APK carries two SFS2X C# libraries, and only one of them is live in 1.0.364 (static-analysis-only):

- **SmartFox2X** is the official SFS2X C# API 1.7.8. The game uses its data model, binary codec, and request envelopes (`ExtensionRequest`, `LoginRequest`, `LogoutRequest`), but never constructs its socket stack.
- **BaseUtils** holds the game's own socket layer and framing (`NetConnection`, `NetPacket` for sending, `NetPacketNew` for receiving), which replaces SFS2X's BitSwarm. There's no `BitSwarmManager` anywhere on the shipping path.
- **Smartfox2xLw** is a 2024 in-house fork of SmartFox2X stripped down to a codec. It's dead code: the only reference to it is a placeholder field that's never assigned, and its system controller has an empty handler table, so it can't even process `Login`. Earlier versions of this page cited it; the citations now point at SmartFox2X and BaseUtils.

`noUpdateAssemblies.json` pins SmartFox2X to the APK copy, so the codec changes only with an app release, unless a hot update replaces that pin list. BaseUtils, which writes the actual frames, can still be replaced through a hot update.

The official SDK's connection sequence also revealed a real gap: it sends a `Handshake` request (action `0`, fields `api`/`cl`, a step this dossier previously called out below as unused) *before* every Login, receiving back a session token / max-message-size / compression-threshold. Sending it against this game's real server got a clean, correctly-shaped response, `{ct=3072, ms=1000000, tk=<32-hex>}`, so the server-side handshake handler is real and working, even though the shipped client never uses it (see below). Practically, though, adding it to the Go client changed nothing: at the time this was tested, the init-push and reconnect-block problems were still unresolved, and this `Handshake` step made no difference to either, guest login and email-bind behaved identically with or without it. Both problems have since been resolved by unrelated fixes (a Zstd decompression bug and a token-identity mismatch, respectively, see [Live validation against production](/live-validation)), confirming the `Handshake` step was never the missing piece.

## Heartbeat & reconnect

A `PingPongRequest` (system controller, action 29) fires every **4000 ms**. On the wire, the real client nests its `clientTime` one level deeper than the action's own `p`: `{c:0, a:29, p:{p:{clientTime}}}` (observed in the 2026-10-04 capture). `goclient` sends it flat, `p:{clientTime}`, and the server answers that too (confirmed live). The pong carries `serverTime` in ms and echoes `clientTime`; the client uses the pair for server-time sync. In the capture, the server answered all 83 heartbeats over 320 s.

Client-perceived timeout is **12s** since the last pong or response, at which point the client disconnects and re-runs the entire connect→login sequence; there is no lightweight session-resume. No exponential backoff was found; retry cadence is a fixed timer.

The 1.0.364 timers (static-analysis-only):

| Timer | Value |
|---|---|
| Keepalive | 4000 ms; the first ping (the probe) goes out immediately on connect |
| Ping-pong timeout | 12 s since the last pong or response, then reconnect |
| `ConnectGame` | 6 s, 3 tries |
| `Login` response | 7 s, up to 3 tries |
| `init` push | 13 s, then reconnect and re-send `Login` with the same `at`, up to 3 times |
| GSL HTTP | 5 s, 4 tries, alternating UnityWebRequest and BestHTTP |

`goclient` sends its first heartbeat 4 s after connecting rather than immediately, waits up to 45 s for `init`, and makes a single attempt. That's more conservative than the real client, and the server accepts it.

## Error conventions

Errors on extension responses are per handler; the 1.0.364 Lua has no generic error layer (static-analysis-only):

- A failed request carries `errorCode`, a UtfString holding either an error code or a locale key.
- An optional `errorPara2` (UtfStringArray) carries tip parameters. The client shows `Localization:GetString(errorCode, table.unpack(errorPara2))`.
- `E000000` is the generic "unknown error" (`SeverErrorCode` in `ConstDefine.lua`). A few handlers treat it as a soft "no data" result, for example a rank preview with nothing to rank.
- `Login` rejections don't use `errorCode`. They arrive as SFS2X's own `ec` (a short) and `ep` (a UTF string array), formatted through the stock SFS2X error table. Code `28` is that table's `"{0}"` passthrough, which carries the game's `E0xx` strings in `ep[0]`, see [Identity, login & session](/auth#login-rejection-codes).
- Fatal conditions come only from the C#: a `Login` rejection, `push.user.off` (kicked: the client quits and doesn't reconnect), `push.server.stop` / `push.server.tostop`, and connection loss.

## Server-controlled transport switches

The check-version response's `client_config` field is a `|`-separated list of `"0"`/`"1"` flags, indexed by switch id (`ClientSwitch.Parse`, see [Startup, version-check & hot-update](/bootstrap)). In 1.0.364, these switches change what goes on the wire (static-analysis-only):

| Index | Name | Effect when on |
|---|---|---|
| 4 | `DISABLE_NEW_NET_PACKET` | The receive path falls back to the old packet class, without Zstd |
| 5 | `DISABLE_ZSTD` | The client stops sending `isUseLz4` in `Login`, so the server doesn't Zstd-compress |
| 20 | named `ENABLE_CDN_SPEED_TEST` | Sets a `tcpSecurityEnabled` value that the 1.0.364 connection constructor ignores |
| 25 | ShuMei SDK on | When off, `shumeiBoxId` is `""` |
| 26 | `ENABLE_SERVER_WS_CONNECTION` | Connect to `ws_ip` on port 80 with connection type 1 |
| 29 | `ENABLE_CROSS_FORWARD` | Together with the Lua switch `EnableServerRangeRouting`, sets the forward bit and server id on every send |
| 44 | `ENABLE_CONNECT_GAME_WEBSOCKET_FALLBACK` | Every second connect retry uses the WebSocket path |

The forward bit in the 2026-10-04 capture suggests switch 29 is on for the iOS app today; the server still accepts `goclient`'s frames without it. `goclient` doesn't parse `client_config`.

**Settled: the shipped client never sends a `Handshake`**

SFS2X's SDK ships a full `Handshake` request (session token negotiation), an AES `CryptoKey` path (`DefaultPacketEncrypter`, keyed over HTTPS from `/BlueBox/CryptoManager`), and a complete MMORoom/AOI (area-of-interest) streaming subsystem. The game uses none of them. The embedded SmartFox2X SDK contains a working `Handshake` (`SendHandshakeRequest`, `SmartFox2X.decompiled.cs:20085-20089`), and the live server answers it when sent (see above), but the game's own transport never calls it. In 1.0.364, `NetConnection` handles only two system actions, `a=1` (`Login`) and `a=29` (ping-pong), and the connect path runs TCP connect, `a=29` probe, then `Login` (static-analysis-only). ## Mini-game PvP transport

Two real-time PvP mini-games, BiuBiu (shooting) and GGGo, don't run over the game socket. They use the `Joker.Share` assembly (static-analysis-only):

1. Matchmaking runs over ordinary SFS2X commands (`activity.shoot.pvp.*`). The reply names a separate server: `ip`, `port`, `sessionidgame`, and `sessionidplayer`, a shape that looks like AWS GameLift.
2. The client connects there over TCP, or in "Hybrid" mode over TCP plus UDP.
3. TCP frames are `u32 LE length | i32 opcode | i32 jsonLen | JSON`.
4. UDP datagrams start with `KCPH` and a channel id, and use kcp2k-style Connect, Data, and Disconnect messages, with an MTU of 470.

This is recorded as a transport fact only. Results in these modes are client-computed, and forging them is out of scope (see [Military, hero & battle](/military-battle)).
