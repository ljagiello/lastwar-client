A scout is an ordinary march. The client sends the same `world.march.formation.new` command as an attack, with `target=17` and a dedicated scout formation that carries no heroes and no soldiers. The server answers with the created march, a mail that holds the report as a base64 protobuf blob, and finally the scout's return.

Everything on this page comes from **one** capture of the real Android app on the real account (server 550), taken with PCAPdroid on 2026-10-22 around 21:01 UTC. The request and response shapes are confirmed live. The meaning of most report fields is **static-analysis-only**: the protobuf has no field names on the wire, and the names below were inferred by cross-checking values. Each one says how sure it is.

## The scout request

```text
world.march.formation.new {
  worldId          = 0
  worldType        = 0
  target           = 17                       // scout (11 is attack a city)
  targetUid        = <uuid of the target world point>
  path             = "186010;182018"          // own city point ; target point
  formationUuid    = <scout_formation uuid>
  formationParam   = { heroInfos = [], formations = [], uuid = <scout_formation uuid> }
  soldierType      = 1
  waitTimeIndex    = -1
  autoBackHome     = true
  targetServer     = 550
  clientCreateUuid = <random GUID v4>
}
```

Differences from the attack captured the same day:

| Field | Scout | Attack |
|---|---|---|
| `target` | `17` | `11` (ATTACK_CITY) |
| `formationUuid` | the account's `scout_formation` (type 2) | a normal squad |
| `formationParam.heroInfos` | empty | one entry per hero |
| `waitTimeIndex` | `-1` | `1` |

The scout formation exists on its own. The server pushes it as `scout_formation` in `push.formation.update.new`: one entry, `type=2`, `heroes=[]`, `soldiers=[]`, `state` 1 while out and 0 once back.

## What the server sends back

In order, all within the same second:

1. `push.formation.update.new` with `scout_formation[0].state = 1`.
2. The `world.march.formation.new` response: the march `uuid`, the echoed `clientCreateUuid`, the account's `resource` block, and a `_proto` byte array (the march's protobuf world record).
3. `push.mail`: the report (see below).
4. `push.army.return` with `scout_formation[0].state = 0`.

The report mail:

| Field | Value |
|---|---|
| `type` | `8` |
| `contentsLocal.b.content.dialog.id` | `311051`, params: `user {name, uid}` and `scout {target: "BASE", targetId: "10100000"}` |
| `contentsLocal.mailId` | `80002` |
| `contentsLocal.obj.scoutContent` | the report: base64 of a protobuf message |
| `title.h.title.dialog.id` / `subTitle` | `300617` / `311104` |
| `custom` | `{"c":{"seasonId":6}}` |
| `expireTime - sendTime` | 259 200 000 ms (3 days) |

`10100000` is the HQ building id, the same `buildId` cities carry on `world.get.block` tiles (see [World map](/world-map)).

## Alliance-shared scout data

`world.get.detail.new` on a city already returns the last scout an alliance member made of it, without sending any march:

```text
allianceScout = {
  scoutData = {
    "data": [ {"id":1,"value":24980}, {"id":14,"value":24980}, {"id":2,"value":11626} ],
    "visible": 1, "defendSize": 1, "defendTotalPower": 0,
    "mailUuid": "<report mail uid>", "mailToUser": "<uid of the scout's owner>"
  },
  endTime = <ms>
}
```

`data` is the lootable resources by resource id: 1 Metal, 14 Food (Bread), 2 Wood (see [Entity ID reference](/entity-id-reference)). This is read-only and needs no march, so a session that can't send marches can still read it.

## The report payload (`scoutContent`)

The C# side has a generated class for it, `LwScoutReport` (see [Findings](/findings)), but that schema isn't in this repo. The tree below was decoded schema-less with `tools/scout-report/pbraw.py`, so only field numbers are known. The names are inferences.

| Path | Meaning | Confidence |
|---|---|---|
| `1.2` | target player name | sure |
| `1.3` | avatar (`player_head_N`) | sure |
| `1.5.1.1` / `1.5.2.1` / `1.5.3.1` | server / X / Y of the target | sure (matches the march `path`) |
| `1.6` | target uid | sure |
| `1.9` | HQ level | likely |
| `1.10` | server | sure |
| `2.1.1` / `2.2.1` | city durability, current / max (10000 = full) | likely |
| `3.1[]` | lootable resources: `.3.1` resource id, `.2.1` and `.4.1` amount | sure (same values as `allianceScout`) |
| `4.1.1[0]` | defending squad 1; `4.1.1[1]` is squad 2 | likely |
| `4.1.1[n].2[]` | heroes of that squad, one entry per slot | sure |
| `…2[].1.1` | hero id | sure |
| `…2[].2.1` | hero level | sure |
| `…2[].4.1` | rank or star step (raw value) | guess |
| `…2[].5.1` | slot 1-5 | sure |
| `…2[].6.1` / `…2[].7.1` | same number, equal to stat `50014` | guess: power or HP |
| `…2[].11[]` | hero stats: `.1` stat id, `.2` float value (absent = flag/zero) | sure (format), names unknown |
| `4.1.4` | one number per squad (24 360 here) | unknown, maybe troop power |
| `4.1.5[]` | soldiers: `.2.1` soldier id (3005-3015 = level 1-11), `.3.1` count (empty = 0) | likely |
| `4.1.7` | one extra stat (`50137` = 1050) | unknown |
| `15`, `16` | account-wide stat lists (`15.4[]`, `16.10[]`) and seven section ids in `16.5[]` | unknown |

### Stat names: `lw_effect_number`

The stat ids are rows of the `lw_effect_number` table (table version 39806), the only table holding all 42 ids below 100000. `find_all.lua` found it on 2026-10-22. Its `name` and `desc` columns are localization keys (`152006`…), and the locale archive wasn't fetched, so the names below come from each row's **icon** and type columns, not from the game's own strings. The `100000`-`100009` ids aren't in `lw_effect_number` (they only collide with unrelated tables such as `battlepass_v2` and `dominator_train_level`), so they stay unknown.

Columns that decode the rows:

- `target_unit_type`: `1` = the hero itself, `2` = the soldiers it leads.
- `target_army_type`: `0` = all, `1` = tank, `3` = aircraft (missile is presumably `2`).
- `type`: `0` = flat value, `1` and `2` = ratio (0.01 = 1 %).
- `name` key: `152006` with the `life` icon = HP, `152007` with `atk_up` = attack, `152009` with `defense` = defense.
- `sequence_equip` / `category_equip 151124`: set on the gear rows.

## Finding cities on the map

All read-only, confirmed live from `goclient` on 2026-10-22:

- The own city's point is `worldMainPoint` in the `init` push (186010 here). Formations are `army_formation` in `init` (one squad, 4 heroes, `soldiers=[]` on that day).
- `world.get.block` around that point returns the tiles. Cities have `pointType=6` and `buildId=10100000`. Their protobuf `BuildInfo` carries: field 4 = HQ level, 7 = allianceId, 11 = shield end (Unix seconds), 13 = durability (10000 = full).
- `world.get.detail.new {point, serverId, worldId, previewAssistance=10, pointType, uid}` returns the player's name, power and alliance, plus `allianceScout` (above). It doesn't return the HQ level or the shield.

## The attack march

```text
world.march.formation.new {
  formationUuid    = <squad uuid>
  target           = 11                       // ATTACK_CITY
  targetUid        = <uuid of the target point>
  path             = "<own point>;<target point>"
  soldierType      = 1
  worldId          = 0
  worldType        = 0
  waitTimeIndex    = 1
  autoBackHome     = true
  targetServer     = 550
  clientCreateUuid = <random GUID v4>          // filled C#-side, SceneManager.World.SaveCreateMarchRecordTime
  formationParam   = { formations = [], uuid = <squad uuid>, heroInfos = [ {index, heroUuid}, … ] }
}
```

This is the field set of two real phone captures, both confirmed live: one on another account (server 67), and one on the real account on 2026-10-22 around 13:29 UTC (target 180010). In both, the server created the march. Right before it, the phone sent `world.get.block`, `world.get.detail.new` and `get.user.info.multi`. No hidden token is in the request.

## Marches from `goclient`: `token error`

The same request from `goclient`, on the same account, was refused every time with `{errorCode=E000000, errorMsg=token error}` and nothing sent (diamonds unchanged). Confirmed live on 2026-10-22:

| # | UTC | What changed | Answer |
|---|---|---|---|
| 1 | — | first try, `clientCreateUuid` = timestamp, no `formationParam` | `token error` |
| 2 | — | `clientCreateUuid` = GUID v4 | `token error` |
| 3 | 13:08 | exact capture format: `formationParam` with 5 heroes, `waitTimeIndex=1`, GUID | `token error` |
| 4 | 13:18 | the capture's own `clientCreateUuid` | `token error` |
| 5 | 13:36 | the phone's sequence in one session: `world.get.block` (OK, target seen: HQ 4, no shield), `world.get.detail.new` (OK), `get.user.info.multi {uids LongArray, allservers 1}` (`E000000`), then the march | `token error` |

The phone's identical request on the same account was accepted 7 minutes before try 5. The parameters, the GUID and the call sequence are ruled out, so the refusal is tied to the `goclient` **session**. The phone's login carries `SecurityCode`, `OneCode`, `CoreV` and `psh`, which `goclient` computes itself (`internal/auth/identity.go`), and the anti-fraud ShuMei fingerprint (see [ShuMei device fingerprint](/shumei)); the server evidently doesn't trust that session for marches. Getting past that check would mean defeating the game's anti-fraud, which is out of scope (see `AGENTS.md`). Attacks, rallies and scouts stay on the phone.

A scout uses the same command, so the same answer is expected. Not tried. Never send `world.march.speed.up`: `useGold=true` spends diamonds.

What `goclient` can do without a march: read the map (above) and `world.get.detail.new`'s `allianceScout`. Joining a rally is a march too (`RALLY_JOIN = 6` in [Entity ID reference](/entity-id-reference)), so the same refusal is expected.

### Decoding a capture that starts mid-session

When the capture starts after the login, the stream doesn't begin on a packet boundary. Dump the raw streams with `pcap -out <prefix>`, then resynchronize on the first offset where three valid SFS2X packets follow each other. The tool used on 2026-10-22 (`resync`) lived in a scratch directory and wasn't kept.

## Reproducing it: commands

`$WORK` is any scratch directory outside the repo. Captures and decodes contain live session secrets (`at`, `SecurityCode`, `OneCode`, `CoreV`, `psh`, `airKey`, `shumeiBoxId`): keep them `chmod 600`, never commit them (`.gitignore` already excludes `*.pcap`), delete them when done.

### 1. Capture

On the phone, PCAPdroid with the Last War app selected, then do the scout in the game and stop the capture. Copy the `.pcap` to the analysis machine.

### 2. Build the decoder (Docker, Go version from `go.mod`)

```bash
cd /opt/lastwar-client/src
GOVER=$(awk '/^go /{print $2}' go.mod)
docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp -e CGO_ENABLED=0 -e GOTOOLCHAIN=local \
  -v "$PWD":/src:ro -v "$WORK":/out -w /src golang:$GOVER \
  sh -c 'go build -trimpath -buildvcs=false -o /out/pcap ./cmd/pcap'
```

### 3. Find the game stream and decode it

```bash
$WORK/pcap -in capture.pcap -list            # the game socket is the "plain" stream on port 10550, usually idx 0
$WORK/pcap -in capture.pcap -stream 0 -decode > $WORK/decoded.txt
grep -n 'world.march.formation.new\|push.mail\|allianceScout\|scout_formation' $WORK/decoded.txt
```

On 2026-10-22 the capture had 3 plain streams and 13 TLS ones; stream 0 (`136.107.113.253:10550`) held 157 client requests, the scout being `#156`.

`-decode` redacts sensitive fields (`Redact()`, first/last 4 characters) and cuts any packet over 50 000 nodes. For a complete, unredacted dump, build a throwaway copy with `tools/scout-report/unredacted-decode.patch` applied, never the deployed binary:

```bash
cp -r /opt/lastwar-client/src $WORK/src-raw && rm -rf $WORK/src-raw/.git
(cd $WORK/src-raw && patch -p1 < tools/scout-report/unredacted-decode.patch)
# then step 2 with -v "$WORK/src-raw":/src:ro and -o /out/pcap-raw
```

### 4. Extract and decode the report

```bash
grep -oE '"scoutContent":"[^"]+"' $WORK/decoded.txt | cut -d'"' -f4 > $WORK/report.b64
python3 -I tools/scout-report/pbraw.py $WORK/report.b64 > $WORK/report.txt            # indented tree
python3 -I tools/scout-report/pbpaths.py $WORK/report.b64 tools/scout-report > $WORK/paths.txt  # one leaf per line
python3 -I tools/scout-report/pbtable.py $WORK/report.b64 > $WORK/table.md   # every leaf: raw bytes | value | meaning (French)
```

`pbpaths.py` prints paths such as `.4[0].1[0].1[0].2[3].1[0].1[0] 40020`; the hero-stat table above is `…2[h].11[i].1[0]` (id) against `…2[h].11[i].2[0]` (value).

### 5. Get the current data tables

`cmd/checkversion` makes the client's anonymous check-version call and prints `table_version` (`version,size,md5,crc;patch chain`):

```bash
# build like step 2 with ./cmd/checkversion, then:
$WORK/checkversion
# 2026-10-22: table_version 39806,19530879,82a8d224c448e8a741f18d1a1b10ad6b,4048400295;…
curl -o $WORK/tables.zip \
  https://lastwar-cdn.akamaized.net/hotupdate/table/table_39806_82a8d224c448e8a741f18d1a1b10ad6b.data
md5sum $WORK/tables.zip     # must equal the md5 above
python3 -I -c "import zipfile,sys; zipfile.ZipFile(sys.argv[1]).extractall(sys.argv[2])" $WORK/tables.zip $WORK/x
```

1 299 tables in 39806 (see [Game data tables](/data-tables)).

### 6. Make the tables loadable

Each table is Lua 5.3 bytecode with the game's modified header (format byte 1, no instruction-size byte; see [Methodology](/methodology)) built for **32-bit** (`size_t` = 4). Fix the header, then load them with a 32-bit `lua5.3`:

```bash
python3 -I tools/scout-report/fix_lua_header.py $WORK/x $WORK/x2     # "fixed 1299 unrecognized 0"
cp tools/scout-report/find*.lua $WORK/
```

A stock 64-bit `lua5.3` (`alpine`) silently loads nothing; `i386/alpine` runs natively on an x86-64 host.

### 7. Look ids up

Loading a table runs it, so do it in a throwaway container with the tables mounted read-only:

```bash
# every table that has any of the ids, with the matching row
docker run --rm -v $WORK:/w:ro -w /w i386/alpine:3.20 \
  sh -c 'apk add -q lua5.3 >/dev/null && lua5.3 find.lua x2 50005 50014 50060 80008 2>&1 | head -60'
```
