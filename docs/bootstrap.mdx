Cold start walks an 18-state machine from splash screen to a live game connection. Four independently-versioned payloads, asset bundles, the C# hot-update assemblies, the Lua bundle, and the data tables, are checked and patched separately, from a single version-check HTTP response.

## State machine (cold start, first launch)

| # | State | Does |
|---|-------|------|
| 1 | `Logo` | Splash screen |
| 2 | `Permission` | OS permission + jailbreak checks |
| 3 | `CheckResVersion` | **Version check**: races N hosts in parallel, first success wins |
| 4–5 | `DownloadManifest` / `DownloadUpdate` | Downloads/patches asset bundles, table data, and the Lua bundle |
| 6 | `LoadDataTable` | Loads config tables + localization into memory |
| 7 | `GetServerList` | **GSL request**: RSA+AES hybrid handshake ([Gate-server RSA+AES handshake](/gate-server-crypto)), on every cold start in 1.0.364 |
| 9 | `ConnectGame` | Races every gateway in the zone's list and keeps the first to answer (see [SFS2X wire protocol](/wire-protocol#gateway-race-and-the-pre-login-probe)) |
| 10 | `Login` | SFS2X `Login` request (see [Identity, login & session](/auth)) |
| 12 | `LoadScene` → `EnterGame` | Loads the actual game scene |

In 1.0.364, `CheckResVersion` clears the cached server IP, port, and connection type on every cold start, so `StartConnect` never finds a cached server and the GSL (Gate Server List) call always runs (static-analysis-only). The cached `ip/port/zone` short-cut from state 6 to state 9 still exists, but only a mid-session reconnect, such as following a `serverInfo` redirect, takes it. See [Identity, login & session](/auth#token-lifecycle) for what the GSL call does with the stored tokens.

## Check-version endpoint

```text
GET {host}/gameservice/getlsu3dversion.php
?packageName=com.fun.lastwar.gp&platform=...&appVersion=...
&gm=0&server=<cached zone>&uid=&deviceId=&table_env=table_online&buildId=<versionCode>
&returnJson=1&unityVersion=440
```

In 1.0.364, `table_env` is `table_online` and `server` carries the cached zone (static-analysis-only). `goclient` now sends the same: `table_env=table_online`, and the session zone in `server` on the cross-server path. Earlier versions sent both empty, and the server answered anyway (confirmed live). The empty `table_env` had one visible cost: the server returns `table_version` and `locale` only when the request carries `table_env=table_online`. Four anonymous check-version GETs on 2026-10-05, Android 1.0.364 and iOS 1.0.344 each with and without `table_online`, showed both fields (plus an empty `x_table_version`) only in the `table_online` variants, with every other field identical (confirmed live).

Host list (requests go out to every host in parallel and the first success wins; on total failure the client retries the same list once). About 5% of devices are A/B-bucketed to the `ea-` hosts by `GrayUtils.GetPercentageFromMd5`: `MD5(deviceId)` read as a little-endian uint64, `mod 100 + 1 <= 5`.

```text
https://lastwar-serverlist-cf.lastwarapp.net
https://lastwar-serverlist-us-aws-ali.lastwargame.com
https://lastwar-serverlist-us-gcp-ali.lastwargame.com

# ea- bucket
https://lastwar-serverlist-ea-us-aws.lastwargame.com
https://lastwar-serverlist-ea-us-gcp.lastwargame.com
```

`goclient` tries the three online hosts one after another, not in parallel.

Whichever host answers becomes the base URL for every subsequent call in this bootstrap (`getserverlist.php`, `getnotice.php`, `probe.php`); there is no separate "gate server" discovery step.

A response counts as valid when it has a non-empty `code` (which the client treats as an error), or when `updateType` is in `0`..`3` and `hotUpdateMsg` is non-empty. The 1.0.364 parser (`CheckResVersionState`) reads these fields:

| Response field | Meaning |
|---|---|
| `code` | Error: the client throws and falls back to the versions packaged in the app |
| `resMsg` | Base64 DER RSA public key (no PEM armor), feeds the GSL crypto, see [Gate-server RSA+AES handshake](/gate-server-crypto). **Not hardcoded**, delivered fresh every check. |
| `updateType` | See the table below |
| `downloadurl` | Store link shown with a forced update |
| `hotUpdateMsg` | `;`-separated `name,version,size,crc32`, asset-bundle manifest versions (`GameRes`, `DataTable`, `Lua`, `Download`, `PackageRes`, `DllRes`). `size` and `crc32` describe the manifest file itself: the APK's `gameres.version` is `2342,18537644,856103597`, where 18,537,644 is the manifest's byte size, and the client writes the three fields verbatim into `<name>.version` (`CheckResVersionState.SaveManifestVersion`; static-analysis-only) |
| `lwfile2` | The Lua bundle: `version\|bzSize\|bzCrc[\|rawSize\|rawCrc];oldVer\|patchSize\|patchCrc;...`. A patch downloads only when the local version equals one of the `oldVer` entries |
| `table_version` | `version,size,md5[,crc][;patch chain]` for the game-data table archive. Returned only when the request carries `table_env=table_online` (confirmed live), see [Game data tables](/data-tables) |
| `locale` | `version,lang1,lang2,...`. Returned only with `table_env=table_online` (confirmed live) |
| `client_config` | Server-pushed feature flags: `\|`-separated `"0"`/`"1"` values indexed by switch id (`ClientSwitch.IsOn(N)` gates throughout the client). See [SFS2X wire protocol](/wire-protocol#server-controlled-transport-switches) for the ones that change the wire |
| `checkok` | Present only in review mode; the client then skips the table and locale updates |
| `warmup` | Opaque asset pre-download list; not protocol-relevant |
| `firstLaunchForceUpdateMsg` | Read only in a first-launch skip-update experiment; not protocol-relevant |

That's every field the parser handles. A live response carries fewer: the iOS check-version response for 1.0.344 (786), fetched on 2026-10-04, held only `client_config`, `downloadurl`, `firstLaunchForceUpdateMsg`, `hotUpdateMsg`, `lwfile2`, `resMsg`, `updateType`, and `warmup`. With `table_env=table_online`, the 2026-10-05 responses also carried `table_version`, `locale`, and an empty `x_table_version` (confirmed live).

`updateType` meanings (1.0.364 C#):

| Value | Meaning |
|---|---|
| `0` | Proceed to download and hot-update |
| `1` | Optional store-update dialog: update or continue |
| `2` | Forced update, blocking. The server no longer accepts this build |
| `3` | Falls into the `default` branch, so it behaves exactly like `0`. The `Login` response handler also rewrites `3` to `0` |

The `Login` response can carry `updateType` too; with `2`, the client enters its app-update state instead of waiting for `init`. On 2026-10-04 the iOS 1.0.344 app got `updateType=3` from both check-version and `Login`, with the `Login` response naming `new_version` `1.0.350` (observed live). `goclient` now logs a warning when check-version returns `updateType=2`, since `Login`s claiming that build are likely to start failing too.

## resVersion

`Login`'s `resVersion` is `GetResVersion()` in the 1.0.364 C# (static-analysis-only):

```text
{GameRes}.{DllRes}_{lwfile2 version}F_{table_version}.{locale}
```

The `{GameRes}.{DllRes}_{lwfile2 version}F` prefix comes from the versions check-version installs: the `GameRes` and `DllRes` manifest versions from `hotUpdateMsg`, and the first `|` field of `lwfile2`. The real iOS app sent `2159.1505_821F_39516.23570` on 2026-10-04, and that day's check-version response returned `GameRes` 2159, `DllRes` 1505, and `lwfile2` version 821, matching the prefix.

The `{table}.{locale}` tail is **local state**, not a field copied from the response (static-analysis-only):

- `{table}` is `CURRENT_TABLE_VERSION`: the APK's built-in `table/version` until a newer table archive has been downloaded, then the highest downloaded version.
- `{locale}` is `LOCALE_VERSION`: the APK's built-in `locale/version` until a downloaded `locale/<ver>/` exists, then the highest such version.

After a successful update, those equal check-version's `table_version` and `locale`, which the server returns only for `table_env=table_online` (confirmed live). On 2026-10-05 a `table_online` request returned table version 39516 and locale 23570, exactly the iOS app's tail. Every part of the 1.0.364 APK's own baseline is in the APK: `2342.1501_825F_39432.23557` (`gameres.version`, `dllres.version`, `LWScripts.txt`, `table/version`, `locale/version`). `goclient` sends `"0"`, which the server has accepted for months.

## Hot-update transport & patch format

Four independently-versioned payloads, compared via the fields above and patched separately:

- **Asset bundles**: UnityFS bundles in the XAssetPro container, tracked by the `gameres` manifest (see [The XAssetPro asset container](#the-xassetpro-asset-container) below).
- **C# assemblies**: the APK ships 118 loose, XOR'd `.mdl` files in `assets/Assemblies/`, not bundles, plus `noUpdateAssemblies.json` = `[{"name":"SmartFox2X"}]`, which pins the SFS2X library to the APK copy. The `dllres` manifest (v1501 in the APK) lists 117 remote-only `<asm>.encrypt.bytes` bundles plus its own copy of that JSON; `mscorlib` has no entry, so it can't be hot-updated. Updated assemblies are written to `persistentDataPath/Assemblies/<asm>.mdl`, which FM_Mono searches before the APK (static-analysis-only).
- **Lua bundle**: one flat `LWLF` file, not wrapped in an AssetBundle at all.
- **Data tables**: the plain-ZIP `table_*.data` archive.

Downloaded patches/replacements may be wrapped in a lightweight on-disk XOR obfuscation (not real confidentiality, key material is hardcoded client-side) built on a **reduced-round ChaCha** stream cipher: 8 rounds (4 double-rounds) instead of standard ChaCha20, IETF layout, detected by a short (3–6 byte) magic-prefix swap:

| Plain magic | Wrapped magic | Content | Keystream starts at |
|---|---|---|---|
| `50 4B 03 04` (`PK··`) | `CHAC` | table `.data` ZIP | byte 4 |
| `42 5A 68` (`BZh`) | `PRB` | bzip2 (Lua bundle package) | byte 4 |
| `42 53 44 49 46 46` (`BSDIFF`) | `PURBDP` | bsdiff patch | byte 8, so bytes 6-7 stay plaintext |

The offsets come from the 1.0.364 `EncryptUtils` in `BaseUtils` (static-analysis-only).

Key/nonce are derived once from hardcoded dummy constants via two self-referential ChaCha8 passes (reproduced independently in Python and confirmed reproducible):

```text
_key   = 83aa6a90bdfb210e4742405500db2c0c80b30776f6441df7cd1504f830ad1f2b
_nonce = 2122232425262728292a2b2c
```

## The XAssetPro asset container

The `gameres` asset bundles aren't plain Unity AssetBundles on disk. XAssetPro (`VEngine`, API 6.1.5) packs them, and the APK's install-time asset pack holds one container. Except for the dated HEAD requests, everything in this section is static-analysis-only, checked against the shipped files:

- `assets/AssetBundles/BundleFragment0.bytes` (539 MB) is 8,059 UnityFS bundles laid end to end, with no gaps or padding. Their headers have the engine version stripped (`5.x.x` / `0.0.0`; the real engine is 2019.4.41f1), and their blocks are LZ4HC.
- `BundleOffsetTable.bytes` and `AliasOffsetTable.bytes` map a bundle's name, or its alias, to `(fragment index << 32) | offset`. Both hold the same 8,059 offsets. The client opens a bundle with `AssetBundle.LoadFromFile(fragment, 0, offset)`.
- Manifests are text, with `[Version]`, `[Directories]`, `[Paths]`, `[Bundles]`, and `[Groups]` sections. A bundle line is `id,name,crc32,size,pathIds,depIds,downloadModes,alias`. The alias is `sha256(name without extension)` plus the extension, and the 32-hex suffix of a bundle's name is the MD5 of its bytes. Each manifest has a `.version` stamp, `version,size,crc32`, which is where `hotUpdateMsg`'s fields land.
- The pack holds exactly the bundles whose `downloadModes` include `0` (`Base`): 8,059 of the 36,745 in the `gameres` manifest (v2342), 539 MB of 3.04 GB. Everything else downloads on demand, by download-mode group.
- Downloads use `<CDN>/hotupdate/com.fun.lastwar.gp/Android/<file>`. A manifest is fetched as the ZIP `<name>_small_v<version>` and CRC-checked against its `.version`. Bundles are fetched by **plain name**; the alias is only the on-device file name. On 2026-10-04, HEAD requests returned 200 for a manifest ZIP and for a bundle by name, and 404 for the same bundle by alias.

<Warning>
TLS certificate validation is disabled on the XAssetPro bundle download path, its `HttpWebRequest` downloader (static-analysis-only). Integrity there rests on the manifest's CRC-32 alone.
</Warning>

## CDN

```text
https://lastwar-cdn.akamaized.net/hotupdate/     (primary)
https://lastwar-cdn.lastwarapp.net/hotupdate/    (fallback)
https://cdn.lastwar.com/hotupdate/               (fallback)
```

The client rotates through the fallback bases on retry. The Lua bundle sits at a predictable path under each base (`NetworkURLConfig.GetDownloadURL`, `LWLuaFileUtil`):

```text
https://lastwar-cdn.akamaized.net/hotupdate/<app id>/<Android|iOS>/LWScripts_<version>_u440.bz2
https://lastwar-cdn.akamaized.net/hotupdate/<app id>/<Android|iOS>/LWScripts_<new>_<old>_u440.patch
```

`<app id>` is the bundle identifier: `com.fun.lastwar.gp` for Android, `com.lastwar.ios` for iOS. The `.bz2` is plain bzip2, not ChaCha-wrapped; if a download ever is wrapped (`PRB`), the client unwraps it first. On disk, the client re-encrypts the bundle as `LWLF` file version 2, which never affects the CDN payload. Old versions stay hosted: every version probed between 780 and 826 returned HTTP 200 on 2026-10-04.

Lua bundle versions seen on 2026-10-04:

| Bundle | `LWLF` version | Chunks |
|---|---|---|
| 1.0.351 APK baseline (recovered from the CDN) | 793 | 18,514 |
| 1.0.364 APK (tag `20260921_1892_App`) | 825 | 18,733 |
| Live Android (newest hosted; 827 and 830 returned 404) | 826 | 18,740 |
| Live iOS (matches the iOS app's `lwfile2`) | 821 | 18,740 |

At the command-catalog level, both live bundles match the 1.0.364 APK. Their differences are debug-only UI modules, a removed diagnostic, and a handful of changed chunks outside `Net/`.
